# Aspotus — архитектура и технологии

## 1. Титульный слайд

Aspotus — платформа каталога автомобилей и запчастей с оформлением заказов, управлением контентом и асинхронными уведомлениями.

## 2. Задача и пользователи

- Покупатель: каталог, корзина, заказ, профиль.
- Модератор контента: автомобили, бренды, поколения, запчасти и справочники.
- Оператор: обработка и статусы заказов.
- Администратор: пользователи, роли, каталог и заказы.

## 3. Как читать схемы

- API Gateway — единая входная дверь: проверяет пользователя и направляет запрос нужному сервису.
- Сервис / API — отдельный модуль, отвечающий за одну бизнес-область.
- База данных — долговременная память конкретного сервиса; общей базы у системы нет.
- Redis — ускоряющий кэш, но не источник истины.
- RabbitMQ — очередь, которая доставляет события между сервисами.
- Worker — фоновый процесс без пользовательского интерфейса.

## 4. Карта системы

Два React-интерфейса обращаются к API через Gateway. За Gateway находятся Catalog API, Orders API и Files API. Catalog использует SQLite и Redis; Orders — SQLite и RabbitMQ; Notifications Worker получает сообщения и хранит Inbox в отдельной SQLite.

## 5. Контейнерная топология

Docker Compose запускает 9 контейнеров в общей backend-сети: два фронтенда, четыре прикладных сервиса, worker, Redis и RabbitMQ. SQLite-файлы и RabbitMQ используют постоянные тома.

## 6. Gateway и безопасность

ASP.NET Core Identity хранит пользователей и роли. Gateway выдаёт JWT, проверяет RBAC, маршрутизирует запросы через YARP и передаёт доверенный пользовательский контекст в служебных заголовках. Внутренний Orders → Catalog API защищён отдельным API key.

## 7. Catalog API

Контроллеры → сервисы → репозитории → EF Core → SQLite. Redis кэширует бренды с graceful degradation. Files API работает с объектным хранилищем. Каталог владеет ценой, остатками и резервами.

## 8. Оформление заказа

Orders API не доверяет цене из браузера. Перед сохранением заказа он резервирует товар в Catalog API и получает серверный снимок названий и цен. Заказ и Outbox-событие сохраняются одной транзакцией.

## 9. Жизненный цикл и резервирование

Created → Processing → Completed. Из Created или Processing возможен Cancelled. Отмена освобождает резерв. Completed финализирует резерв; проданный автомобиль скрывается от покупателя, но остаётся в административном каталоге.

## 10. Асинхронные уведомления

Transactional Outbox устраняет разрыв между записью заказа и публикацией события. RabbitMQ доставляет OrderCreated в durable-очередь. Notifications Worker использует Inbox для идемпотентной обработки повторных доставок.

## 11. Владение данными

- Gateway DB: Identity, пользователи и роли.
- Catalog DB: каталог, изображения, остатки и резервы.
- Orders DB: заказы, снимки позиций и Outbox.
- Notifications DB: обработанные сообщения Inbox.

Межсервисного доступа к чужим БД нет.

## 12. Клиентские приложения

Customer Web и Admin Web построены на React и Vite. Customer Web использует React Bootstrap, Admin Web — Material UI. JWT и ролевые маршруты разделяют пользовательские сценарии.

## 13. Надёжность и эксплуатация

Автомиграции, health checks инфраструктуры, компенсирующее освобождение резерва, повторяемые операции, Redis fallback, единая обработка исключений, Swagger и сохранение данных вне контейнеров.

## 14. Тестирование

157 backend unit/controller tests, 56 Customer Web tests, 50 Admin Web tests. Vitest + Testing Library проверяют компоненты, Playwright — сквозные пользовательские сценарии в Docker Compose.

## 15. Технологический стек

.NET 10, ASP.NET Core, EF Core, SQLite, YARP, Identity, JWT, Redis, RabbitMQ, React 19, Vite 8, Material UI, React Bootstrap, Docker Compose, xUnit, Moq, AwesomeAssertions, Vitest и Playwright.

## 16. Развитие

Production secrets, PostgreSQL, OpenTelemetry, централизованные логи, retry/circuit breaker, DLQ, versioned API, CI/CD и оркестрация контейнеров.

## 17. Итог

Aspotus разделяет ответственность, данные и пользовательские роли; сочетает синхронные операции с надёжной асинхронной доставкой и сохраняет возможность постепенно усиливать production-ready свойства.
